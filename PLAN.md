# План минимальной реализации мини-CRM

Источник: https://docs.google.com/document/d/1dpyRJ1E__eD0cisYSj0GDml4xtTTPaLe/edit

## Цель и границы

За ориентировочные 2–3 часа сделать небольшое работающее приложение для строительной компании. Приоритет — обязательные сценарии, доступ к данным и корректная смена статусов. Дизайн по ТЗ не оценивается: достаточно понятных форм, списков и кнопок.

Минимальная реализация готова и опубликована на https://mini-crm-drab-mu.vercel.app. Сборка и 10 локальных тестов базы проходят; облачный Supabase проверен от имени трёх пользователей — 71 проверка прошла. Проверены анонимный доступ и основные экраны в браузере. Результаты — в `docs/VERIFICATION.md`. План ниже сохранён как описание исходного объёма работ.

## Обязательный функционал

- Вход по email и паролю, выход. Открытая регистрация отключена.
- Несколько постановщиков и исполнителей. Постановщик видит все объекты и задачи; исполнитель — свои задачи и объекты, где они есть.
- Создание, изменение и удаление объектов и задач постановщиком. У объекта — название и адрес. У задачи — название, описание, объект, один исполнитель, статус, автор и дата создания.
- Строго заданные переходы статусов и обязательный комментарий при возврате на доработку.
- История смены статусов: пользователь, время, старый и новый статус, комментарий. Исполнитель видит историю только доступной ему задачи.
- Пять экранов: вход, объекты, объект с задачами, задача с историей, мои задачи.
- Работающее приложение, GitHub-репозиторий, SQL-миграции, короткий README, демонстрационные данные, объяснение для руководителя и список допущений.

## Техническое решение

- Vite + React + TypeScript.
- React Router для пяти экранов.
- Supabase Auth, PostgreSQL и RLS; запросы через `@supabase/supabase-js`.
- Обычный CSS и стандартные элементы форм. Данные загружаются простыми запросами на нужных экранах.
- Один фронтенд и один проект Supabase. Отдельный сервер не нужен.

Без Redux, отдельного API-сервера, микросервисов, универсальных CRUD-конструкторов и собственной системы авторизации. Не добавляем поиск, фильтры, пагинацию, Kanban, уведомления, файлы, регистрацию и управление пользователями через интерфейс: этого нет в ТЗ.

## Данные и безопасность

Четыре таблицы:

| Таблица | Основные данные |
| --- | --- |
| `profiles` | ID пользователя из Auth, отображаемое имя, роль `manager` или `executor` |
| `objects` | ID, название, адрес |
| `tasks` | ID, название, описание, объект, исполнитель, статус, автор, дата создания |
| `task_status_history` | ID, задача, кто изменил, время, старый и новый статус, комментарий |

RLS включается на всех таблицах. Анонимные запросы к данным запрещены. Роли задаются при ручной подготовке пользователей и не редактируются клиентом. Постановщику доступен минимальный список исполнителей для назначения; исполнителю — только необходимые ему данные профилей.

Постановщик может создавать, редактировать обычные поля и удалять задачи и объекты. Исполнитель не может напрямую редактировать задачи. Вставка задачи проверяет роль, начальный статус, автора и роль назначенного пользователя. Автор и дата создания задаются системой и не доступны для последующего изменения из клиента.

Смена статуса выполняется одной SQL-функцией `change_task_status(task_id, next_status, comment)`, вызываемой через Supabase RPC. Функция проверяет текущего пользователя, роль, назначение, текущий статус и комментарий. Она блокирует строку задачи на время операции и атомарно меняет статус и добавляет запись истории. Прямое изменение столбца статуса через API закрывается правами на столбцы; обычное редактирование разрешается только для явно перечисленных полей.

Для функции с повышенными правами задаются безопасный `search_path`, явные проверки полномочий и доступ к вызову только для `authenticated`. Идентификатор автора действия и время берутся на стороне базы. Запись о создании задачи с переходом из пустого статуса в `new` добавляется триггером. Пользовательские INSERT, UPDATE и DELETE истории запрещены.

Во фронтенде используются URL Supabase и публичный publishable/anon-ключ. `service_role`, пароли тестовых пользователей и прочие секреты не коммитятся. В репозитории — только `.env.example` с пустыми значениями.

## Статусы

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| — | Новая | Постановщик | Создание задачи |
| Новая | В работе | Назначенный исполнитель | — |
| В работе | На проверке | Назначенный исполнитель | — |
| На проверке | Принята | Любой постановщик | — |
| На проверке | На доработке | Любой постановщик | Непустой комментарий после trim |
| На доработке | В работе | Назначенный исполнитель | — |

Все остальные переходы запрещены. На экране задачи отображаются только доступные кнопки. После изменения статуса данные и история перечитываются.

## Порядок работ

1. **Каркас и Auth — 20 минут.** Создать Vite-проект, подключить Supabase и роутер, сделать вход и выход, загрузку роли и защиту маршрутов. Подготовить облачный проект, отключить регистрацию.
2. **База и ограничения — 50 минут.** Одна начальная SQL-миграция: таблицы, ограничения, RLS, права на столбцы, функция смены статуса и запись истории создания. Подготовить минимум одного постановщика, двух исполнителей, 2–3 объекта и задачи в разных статусах. Задачи проводить по разрешённым переходам, чтобы история соответствовала статусам.
3. **Пять экранов — 55 минут.** Список объектов, карточка объекта и задачи, мои задачи; формы создания и редактирования; удаление с подтверждением. На карточке задачи — действия по роли и статусу, комментарий при доработке, история. На всех формах — базовая валидация, состояние загрузки и понятная ошибка.
4. **Проверка сценариев и защиты — 30 минут.** Пройти полный цикл задачи. Проверить доступ и запрещённые действия прямыми запросами к Supabase от имени разных пользователей. Исправить найденное, проверить сборку.
5. **Сдача — 25 минут.** Развернуть фронтенд, проверить облачную версию, подготовить README и текст для руководителя, записать допущения, собрать ссылки и тестовые доступы в одно сообщение.

Ориентир — 3 часа при готовых аккаунтах Supabase, GitHub и хостинга. Настройка доступов и непредвиденные проблемы могут увеличить время. При нехватке времени упрощаем внешний вид, сохраняя обязательную логику и защиту.

## Что проверить

- Постановщик создаёт, редактирует и удаляет объекты и задачи; может назначить только исполнителя.
- Исполнитель A видит свои задачи и связанные объекты. На общей с исполнителем B стройке он не видит задачи B; прямой запрос по известному чужому ID тоже не раскрывает данные.
- Исполнитель не может назначить себя на чужую задачу, менять обычные поля задачи или свою роль.
- Полный цикл: новая → в работе → на проверке → на доработке → в работе → на проверке → принята.
- Возврат без комментария или с одними пробелами, пропуск стадии, повторный переход и действия другого исполнителя отвергаются базой.
- Прямой UPDATE статуса отвергается даже для постановщика; разрешённые изменения обычных полей работают.
- Историю нельзя вставить, изменить или удалить прямым запросом. Ошибка перехода не создаёт запись истории; повторная отправка не создаёт дубли.
- После смены исполнителя предыдущий теряет доступ к задаче и, если других его задач на объекте нет, к объекту.
- Без входа данные недоступны, открытая регистрация выключена, в сборке нет секретного ключа.
- После обновления страницы пользователь остаётся в сессии; после выхода защищённые экраны недоступны.

Для проверки прав использовать реальные пользовательские сессии и публичный ключ: запросы из SQL Editor с административными правами не доказывают работу RLS.

## Принятые допущения

- Все постановщики имеют одинаковые права и могут работать с любыми объектами и задачами.
- У задачи один обязательный исполнитель. Автор и дата создания неизменяемы; принятая задача имеет конечный статус без повторного открытия.
- Постановщик может менять исполнителя и обычные поля в любом статусе; это само по себе не меняет статус. История фиксирует смену статусов, а не каждое редактирование полей.
- Удаление объекта с задачами запрещено: сначала нужно удалить задачи. Удаление задачи удаляет её историю каскадно. Запрет удаления истории трактуется как запрет её самостоятельного изменения через API; такое допущение нужно явно указать при сдаче.
- Отдельного экрана пользователей нет: тестовые аккаунты и роли создаются вручную в Supabase.
- Формы создания и редактирования размещаются на имеющихся экранах или в простых диалогах; дополнительные страницы не нужны.
