# Мини-CRM «Объекты и задачи»

React + TypeScript + Supabase. Постановщики управляют объектами и задачами, исполнители работают со своими задачами. Доступ и переходы статусов проверяются в PostgreSQL.

## Локальный запуск

Нужен Node.js 20.19+ или 22.12+ и npm. Файл `.nvmrc` выбирает актуальную версию Node.js 22.

```sh
npm ci
cp .env.example .env.local
npm run dev
```

В `.env.local` укажите параметры из проекта Supabase:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_OR_ANON_KEY
```

Подходит публичный ключ `sb_publishable_…` или прежний JWT `anon`. После изменения `.env.local` перезапустите Vite. Без параметров приложение показывает инструкцию подключения. Все `VITE_*` значения доступны посетителям: секретные ключи сюда не помещать.

## Подготовка Supabase

1. Создайте проект на [supabase.com](https://supabase.com).
2. Примените миграции через Supabase CLI: один раз выполните `npx supabase init` для создания локального `supabase/config.toml`, затем `npx supabase login`, `npx supabase link YOUR_PROJECT_REF`, затем `npx supabase db push --remote`. CLI выполняет файлы из `supabase/migrations` по порядку и записывает их в журнал миграций. Если выполняете SQL вручную через SQL Editor, после успешного выполнения каждой миграции отметьте её через `npx supabase migration repair VERSION --status applied --remote` в подключённом проекте: сам SQL Editor журнал не обновляет. Не запускайте миграции повторно в уже настроенной базе.
3. В Authentication → Sign In / Providers отключите **Allow new users to sign up**. В разных версиях панели этот переключатель может находиться в настройках email-провайдера. Отсутствие формы регистрации во фронтенде само по себе не отключает регистрацию через Auth API.
4. В Authentication → Users → Add user создайте трёх пользователей с email и собственными паролями; включите Auto Confirm User:
   - `manager@example.com`
   - `executor1@example.com`
   - `executor2@example.com`
5. Выполните `supabase/seed.sql`. Он назначит роли, создаст 3 объекта и 6 задач с корректной историей и всеми пятью статусами. Один объект доступен только второму исполнителю; на общих объектах задачи других исполнителей скрыты. Повторный запуск не дублирует данные, если демонстрационные объекты сохранены.
6. В настройках Auth задайте Site URL адресом опубликованного приложения. Получите Project URL и публичный ключ в настройках подключения/API и добавьте их в `.env.local`.
7. Войдите под каждым аккаунтом. Секреты и пароли не добавляйте в репозиторий; передавайте тестовые доступы заказчику отдельно.

Для дополнительных пользователей: создайте аккаунт в Auth, затем доверенным запросом в SQL Editor добавьте `profiles` с его UUID, именем и ролью `manager` или `executor`. Не используйте пользовательские metadata для определения роли. Редактирование ролей через клиентский API закрыто.

## Обновление существующей базы

В Supabase CLI 3.x команды базы без `--remote` обращаются к локальному PostgreSQL (`127.0.0.1:54322`). Для облачного проекта явно указывайте `--remote`; одного `link` недостаточно. [Выбор локального или облачного проекта](https://supabase.com/docs/guides/local-development/local-and-hosted-projects).

Если начальная миграция уже применена и записана в журнале, выполните `npx supabase db push --remote`: будет применена только `202611040002_preserve_task_history.sql`. Сначала обновите базу, затем опубликуйте новую сборку фронтенда. Миграция сохраняет существующие задачи и историю, добавляет архив и закрывает физическое удаление через пользовательский API. Ранее удалённую историю она восстановить не может.

### Ошибка `type "user_role" already exists` в Supabase Preview

Такая ошибка при выполнении `202611040001_initial.sql` означает, что тип уже существует в целевой базе. Если начальную миграцию ранее выполнили через SQL Editor, её SQL уже применён, но в журнале `supabase_migrations.schema_migrations` может отсутствовать запись. Интеграция GitHub тогда пытается выполнить её повторно.

Для базы, в которой **вся начальная миграция уже успешно выполнена**, синхронизируйте журнал:

```sh
# Один раз, если supabase/config.toml ещё нет:
npx supabase init
npx supabase login
npx supabase link YOUR_PROJECT_REF
npx supabase migration list --remote
npx supabase migration repair 202611040001 --status applied --remote
npx supabase db push --dry-run --remote
```

Убедитесь, что dry-run предлагает только ещё не выполненную миграцию архива `202611040002_preserve_task_history.sql`. Затем выполните `npx supabase db push --remote` и повторите GitHub-проверку Supabase Preview. Команда `migration repair` меняет только журнал; таблицы, данные и историю задач она не меняет.

Если миграция архива тоже уже успешно выполнена вручную, отметьте её отдельно командой `npx supabase migration repair 202611040002 --status applied --remote`; повторно выполнять её SQL нельзя. Если начальная схема создана частично или отличается от миграции, сначала проверьте различия — одного существующего типа недостаточно для отметки всей миграции. Используйте проект или ветку из ссылки Details упавшей проверки. Не удаляйте существующие типы/таблицы и не выполняйте сброс базы для устранения этой ошибки.

## Проверка и сборка

```sh
npm test
npm run build
npm run preview
```

`npm test` запускает настоящую PostgreSQL-базу в WebAssembly через PGlite и применяет производственные миграции. Проверяются RLS, права на столбцы, полный цикл статусов, запрещённые переходы, неизменяемость истории, смена исполнителя, обновление существующей базы и сохранение истории после архивирования задачи и объекта. Supabase `auth.users` и `auth.uid()` воспроизводятся небольшим тестовым окружением. Тестам не нужны облако, Docker и секретные ключи.

Эти проверки не заменяют проверку облачного Auth и REST API. После подключения Supabase выполните сценарии из `docs/ACCEPTANCE.md`, включая прямые API-запросы от имени разных пользователей и попытку регистрации.

## Как защищены данные

- RLS включён на всех четырёх таблицах. Исполнитель читает только свои задачи и связанные объекты. На общем объекте чужие задачи остаются недоступны.
- Роли находятся в защищённой таблице профилей. Клиент не может присвоить себе роль постановщика.
- Постановщик может менять только явно разрешённые поля. ID, автор, дата создания и статус не доступны для прямого изменения через API. Новые задачи получают системного автора, дату и статус `new`.
- Смена статуса выполняется только через `change_task_status`. Функция проверяет пользователя, роль, назначение, переход и обязательный комментарий; блокирует задачу на время операции; записывает статус и историю одной транзакцией.
- Задачи и объекты архивируются через `archive_task` и `archive_object` только постановщиком. Прямое удаление через пользовательский API запрещено. Архивные записи доступны постановщикам только для чтения; исполнители не видят их и не могут менять их статусы.
- История доступна только для чтения и только через доступную задачу. Архивирование не меняет и не удаляет историю; внешний ключ запрещает каскадное удаление. Автор действия и время берутся на стороне базы.
- Функции с повышенными правами имеют пустой `search_path`, явные проверки прав и ограниченный доступ. Внутренние функции находятся в отдельной схеме. Оставьте `private` вне списка exposed schemas в настройках Data API.
- Во фронтенде используется только публичный ключ. Административный доступ владельца Supabase остаётся доверенным: RLS не предназначен для ограничения владельца базы.

## Деплой

Фронтенд статический, отдельного сервера нет. Подойдут Vercel или Netlify:

1. Разместите исходники в GitHub и импортируйте репозиторий на хостинг.
2. Добавьте две переменные из `.env.example` в настройки окружения.
3. Команда сборки: `npm run build`. Каталог результата: `dist`. Версия Node.js на хостинге: актуальная 22 LTS (не ниже 22.12).
4. Настройки SPA-переадресации уже есть: `vercel.json` и `public/_redirects` для Netlify. Прямое открытие `/tasks/:id` должно возвращать приложение.
5. Проверьте вход, обновление вложенных страниц, оба типа ролей и весь цикл задачи на опубликованном адресе.

## Решения и допущения

- Все постановщики равноправны и могут изменять задачи друг друга.
- У задачи один обязательный исполнитель. Назначать можно только профиль с ролью `executor`.
- Все статусы меняются только по ТЗ. `accepted` — конечный статус; повторное открытие не предусмотрено.
- Обычные поля и исполнителя можно менять в любом статусе, без сброса статуса. Автор и дата создания неизменяемы.
- История фиксирует создание и смену статуса. Изменение описания, назначения и других полей отдельной историей не сопровождается.
- Удаление реализовано как архивирование без возможности восстановления через клиентский API. Задача исчезает из рабочих списков, но её данные и история сохраняются. Объект можно архивировать после всех его активных задач. Постановщик открывает архив объектов из списка объектов, архив задач — из карточки объекта. Архивные карточки доступны только для просмотра.
- Отдельных экранов регистрации, пользователей, поиска и фильтров нет. Списки загружаются целиком: для объёма тестового этого достаточно.
- Интерфейс обновляет данные после собственных операций и при открытии экрана. Автоматическое обновление действий других пользователей через Realtime не реализовано; база всё равно проверяет актуальный статус.
- Аккаунты и Supabase-проект создаются владельцем вручную. Результат проверки предыдущего облачного развёртывания записан в `docs/VERIFICATION.md`; изменение архивирования требует применения второй миграции, публикации фронтенда и повторной облачной проверки.
